# antigravity fork 修复：技术方案（中档）

任务 desk-a310a30f，父任务 desk-9120ee84。对应 PRD 1017、1018、1019（已审，见 my-superagent docs/PRD/README.md「任务主会话可以用 Antigravity 模型」）。

定档：中档。判据：跨模块（pool、settings、设置卡片、二进制解析、官方进程环境）；动了被多处调用的调度机制（PooledAcpAdapter）。

## 三处改动

### A. 去掉并发上限（需求 1019，用户原话「去掉代码中的并发限制」）

- `src/pool/pooled-adapter.ts`：删掉 `capacity`（夹在 1–4 的 worker 上限）、64 项队列上限（`AGY_QUEUE_FULL`）、排队超时（`queueTimeoutMs` / `AGY_QUEUE_TIMEOUT`）。没有空闲 worker 时一律新开一个。
- 新对话选哪个 worker：上游在容量没满时宁可新开 worker，也不接管别的对话正在复用的 worker（粘性）。没有上限后「容量没满」永远成立，照原样每个新对话都会新开一个槽位，槽位数跟着对话数一直涨（`listModels`、`resolveModel`、`read` 都要遍历全部槽位），每个新对话都要冷启动。改成按这个顺序挑：自己粘着的空闲 worker → 没服务过任何对话的空闲 worker → 官方进程已经回收（`processRunning` 为 false）的空闲 worker → 新开一个。进程已回收的 worker 上没有可复用的 ACP 会话了，交给新对话不损失什么。这样槽位数不超过同时活着的官方进程数的峰值。关闭粘性（`reuseSessions` 关）时照旧：先用空闲的，没有就新开。
  - 另一种做法：照原样无条件新开，代码不动。不选，理由见上：槽位无界增长。
  - 判断靠 `worker.read().processRunning`：`lifecycle.stopped()` 置 false，进程空闲回收、异常退出、取消回收都会走到。判错的情况：进程刚被回收、新对话还没来之前，粘着它的老对话回来了，老对话照样走「自己粘着的空闲 worker」，不受影响。
- 还会等的只剩一种：同一个会话（同一 owner）的两个请求重叠，后一个等前一个结束（ACP 会话状态在 worker 内部，不能并行）。这不是会话之间的排队，1019 管不到；这种等待可以靠 signal 取消，前一个请求本身有 `promptTimeoutMs`，所以不再单独设超时。
- `src/settings.ts`：删掉 `maxConcurrentSessions`、`queueTimeoutMs` 两项配置（含 `Settings` 接口里的字段）。旧配置里留着这两个键：schemastery 的 object 会丢掉不认识的键，上游删 `cloakSensitiveWords` 时也是这样做的。
- `src/index.ts`：不再传 capacity 和 queueTimeoutMs。
- `src/runtime/lifecycle.ts`：快照里的 `queue.capacity` 删掉。`src/client.js` 的「并发连接 workers / capacity」改成只显示 workers；`PLAIN_FIELD_LABELS` 删掉这两项；`src/client-i18n/en-ui.js` 删掉对应的词条。
- 文档：`docs/configuration.md` 删掉这两行，并写明 worker 按需启动、没有上限，空闲 `idleRecycleMs`（默认 5 分钟）后回收官方进程；`docs/reference.md` 删掉 `AGY_QUEUE_TIMEOUT` / `AGY_QUEUE_FULL`。
- 内存：每个官方进程约 170MB。worker 槽位本身不回收，但官方进程空闲 5 分钟后由 `#scheduleIdleRecycle` 回收（`antigravity-adapter.ts` 第 1044 行），所以常驻内存跟着最近 5 分钟内的并发峰值走，不会一直涨。

依赖它的地方（grep `capacity|maxConcurrentSessions|queueTimeout|AGY_QUEUE`）：上面列的源码、`tests/pooled-adapter.test.ts`、`tests/client-interaction.test.ts`（第 429、718 行）、`tests/settings-schema.test.ts`。逐处跟着改。

被删掉的行为和对应用例：
- 「第三个会话排队」→ 改成「第三个会话立即开新 worker 并行」（红测，需求 1019）。
- 队列满拒绝、排队超时：行为删除，删掉这两个用例。
- 标题请求排在前台之后（只在容量满时才有意义）：容量不再满，删掉。
- 预热占着 worker 时聊天排队、目录读取排在 parked owner 后面：改成聊天 / 目录读取另开 worker 立即开始。（实现时发现：在 main 上默认容量是 2，这两种情况本来就会另开 worker，所以它们不是红测，只是把原来用 `capacity: 1` 测的用例改写过来。在 main 上失败的、被改变的行为是「超过上限也并行」和「接手进程已回收的 worker」两条。）
- 其余用 `capacity: 1/2` 的用例：去掉 capacity 参数，断言不变时照旧通过。

### B. 解压后给所有文件补执行位（需求 1018）

- 实测：官方 1.4.0 macOS 包解出 `agy_acp_server.par` 和 `localharness_external` 两个文件；插件只对挑出来的主程序 chmod，`localharness_external` 留在 0644，运行时报 Permission denied。
- 做法：posix 下对解压目录里的每个普通文件 chmod 0755，下载、并发提交（winner）和命中缓存三条路径都做。命中缓存也做，这样已经解压过的缓存（例如 3093 上的那份）在下次启动时自己修好。
- 另一种做法：解压时按 zip 条目的 unix 权限位恢复。不选：要读 externalFileAttributes，且官方 zip 是否带了执行位没有实测；而且修不了已有的缓存，缓存路径还是得补 chmod。
- 承诺范围：只管插件自己解压的 extract 目录；`binaryPath` / `AGY_ACP_BIN` 指定的二进制由用户负责，不改权限。

### C. 官方进程环境加 AGY_ACP_FORCE_FILE_STORAGE=1（需求 1017）

- 实测（父任务在 3093 上）：不设时官方 server 1.4.0 在 macOS 上不读 `~/.gemini/antigravity-acp/acp_token.json`，session/new 打出「Credentials missing or invalid. Launching browser login flow...」，150 秒超时；设了以后 3–4 秒成功。
- 做法：`officialAgentEnv` 里固定设 `AGY_ACP_FORCE_FILE_STORAGE=1`，所有平台都设。插件在所有平台上都把登录态写成这个文件，让官方 server 读文件就是插件本来的意图；Windows 上目前不设也能用，说明那里默认就读文件，设了没有坏处。
- 另一种做法：只在 macOS 上设。不选：Linux 上没有实测，分平台会多一个分支；而且插件在所有平台上本来就靠这个文件。
- 不能实测的：Linux、Windows 上设了这个变量后的行为。
